TP=2 vs DP=2 on 2x RX 7900 XTX — initial conclusion
Date   : 2026-09-19
Model  : Qwen3.8-27B-W4A16-AutoRound-GPTQ (19 GB on disk, W4A16 GPTQ)
Hardware: 2x Radeon RX 7900 XTX, 24 GB each; patched kernel 7.0.14-x99p2p

═══════════════════════════════════════════════════════════════════════════
VERDICT
═══════════════════════════════════════════════════════════════════════════
TP=2 works and is the only usable dual-GPU profile.
DP=2 as currently configured CANNOT start — it is not a tuning problem, it is
a hard capacity limit. Details below.

═══════════════════════════════════════════════════════════════════════════
TP=2 — measured
═══════════════════════════════════════════════════════════════════════════
Benchmark: bench/bench-concurrency.py, 256 output tokens per request,
ignore_eos, PROMPT is a fixed long-form generation request.
"aggregate" = total output tokens / wall clock across all concurrent streams;
"per-stream" = mean per-request decode rate excluding its own TTFT.

  conc  reqs   wall   aggregate   per-stream   TTFT p50   TTFT max
  ────  ────  ─────   ─────────   ──────────   ────────   ────────
     1     4   14.0s      31.8       34.5       0.26s      0.31s
     2     8   21.6s      41.0       27.7       0.47s      4.16s
     4    16   21.9s      78.7       21.6       0.31s      0.53s

  Scaling c=1 -> c=4 gives 2.5x aggregate. Per-stream decode falls 34.5 ->
  21.6 tok/s as batch grows, which is expected: the two cards are already
  saturated, so extra concurrency buys aggregate throughput by interleaving
  rather than by going faster per request.

  Earlier end-to-end figure (non-streaming, 400 tokens): 77.7 tok/s, with
  engine-reported steady-state decode of 73-103 tok/s. Consistent with the
  c=4 aggregate above.

  Memory at TP=2: 9.12 GB weights per GPU, ~21 GB/GPU total including KV
  (195k tokens) and mamba state, at --mem-fraction-static 0.90.

  Caveat on the c=2 row: TTFT max of 4.16s is a warm-up outlier (first
  request after a profile switch still compiling kernels). Re-runs settle to
  the c=1/c=4 TTFT range.

═══════════════════════════════════════════════════════════════════════════
DP=2 — FAILS TO START (capacity, not tuning)
═══════════════════════════════════════════════════════════════════════════
Each DP instance must hold the ENTIRE model on one card. The launcher's
shared serve_args include --mem-fraction-static 0.90, so SGLang plans for
0.90 x 24 GB = 21.6 GB of that card. The 19 GB checkpoint, once loaded and
padded, leaves a NEGATIVE remainder for the hybrid state cache:

  RuntimeError: Not enough GPU memory for hybrid (mamba/linear-attention)
  state cache. Computed max_mamba_cache_size=-18
  (total_rest_memory=-4.84 GB, mamba_cache_per_req=146.81 MB)

  rest_memory = -4.84 GB  =>  the model + reserved overhead already exceeds
  the 0.90 budget before any KV or mamba state is allocated.

Why TP=2 does not hit this: sharding splits the weights, so each card holds
only 9.12 GB of them and has room for KV and state. This is precisely the
capability P2P unlocks, and why the three P2P layers matter here.

Options if DP=2 is genuinely wanted (none tested yet, all speculative):
  a) Lower --mem-fraction-static for the DP profile. Unlikely to be enough:
     the deficit is 4.84 GB, and dropping the fraction also shrinks the KV
     budget it is meant to protect.
  b) Lower context length (196608 is a TP=2-sized choice) and drop MTP, to
     cut the per-request state. This is the most plausible route.
  c) Accept a smaller/less quantized model for DP, or use only one DP
     instance and leave the other card free (that is the sglang-single
     profile).
  d) 4-bit KV cache instead of bf16 to shrink KV — but the fork explicitly
     warns against FP8 KV on RDNA3, so this needs care.

The honest summary: on this node, "2 GPUs" means "one 27B model served with
TP=2", not "two independent 27B servers".

═══════════════════════════════════════════════════════════════════════════
Measurement notes (pitfalls hit while producing this)
═══════════════════════════════════════════════════════════════════════════
1. Count reasoning_content as output. This model streams a thinking channel;
   counting only `content` undercounted output by ~40% and made c=1 look
   like 27.9 tok/s aggregate when the real figure is 31.8.
2. A profile switch holds the hub's lock. Killing the curl client does NOT
   cancel it server-side; subsequent switches return HTTP 409 until it
   finishes. Wait, do not retry.
3. The launcher must be started detached (setsid). A launcher tied to a
   short-lived shell takes its `docker run --rm` containers down with it,
   which looks exactly like "the containers died on their own".
4. Setting HOME is mandatory for these containers. Without it torch tries to
   create a cache under /home/<user>, which does not exist in the image, and
   the process dies at import with PermissionError on /home/unknownue. The
   launcher sets HOME=/cache; ad-hoc `docker run` probes must too.
