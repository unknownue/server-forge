## Project Overview
`server-forge` is an Infrastructure-as-Code (IaC) repository for provisioning, configuring and
maintaining the user's own multi-machine fleet — bare-metal servers and workstations alike.
Machines may serve very different purposes (development, compute, storage, always-on services),
and each one keeps its own reproducible configuration here.
Core philosophy: **fully reproducible, script-driven machine configuration** — no manual data
backup, only configuration scripts and version control are used to rebuild any node from scratch.

## Per-Node Configuration
Each node directory contains the machine's complete environment:
- `hardware-info.txt` — full hardware report generated by `scripts/lib/hardware-info.sh`
- `README.md` — machine-specific configuration (OS, drivers, roles, maintenance log)
- Provisioning scripts, service launchers, and workload registries, as that machine needs
- Refer to individual node directories for all machine-specific details.

**This file describes conventions shared by every machine only.** Anything specific to one
machine — hardware, drivers, installed services, workload deployment, known pitfalls and their
fixes — belongs in `nodes/<hostname>/README.md`, never here.

## Configuration Management Principles
1. **Everything as code** — all machine configuration is version-controlled.
2. **Back up configs, not data** — data volumes (container images, cloned repositories,
   databases, downloaded artifacts) are ephemeral and rebuildable via the configuration code
   maintained in this repository. Only the provisioning scripts are version-controlled;
   the data they produce is not.
3. **Leave headroom** — always reserve unallocated capacity for online expansion.
4. **Persist configs** in each node's directory and apply them to system paths during provisioning.
5. **Temporary files** generated during processing (logs, intermediates) must be written
   to the project `tmp/` directory, never to system `/tmp/` or working directory root.

## Shared Data Layout

Nodes with dedicated data volumes follow a two-tier split, regardless of workload:

| Path | Content | Rebuild cost |
|:---|:---|:---|
| `/data/work/` | Persistent work products: repositories, models, datasets, checkpoints, databases | Expensive — keep, but still reproducible from config |
| `/data/cache/` | Disposable caches: kernel/compile caches, package caches, container scratch | Free — drop and rebuild at will |

Provisioning that allocates these volumes is per-node (`nodes/<hostname>/provision/`),
because the mechanism differs by machine (LVM, btrfs subvolume, plain directories).
Never assume either path exists until the node's provisioning script has been run.

## Docker Container File Ownership

When containers write to host-mounted directories (`-v /host/path:/container/path`),
files created inside the container are owned by the container's user (typically root),
causing "Permission denied" errors for subsequent host-side operations.

### Pattern 1: Run as host user (preferred)

Use `--user $(id -u):$(id -g)` so the container process runs as the host user.
Combine with `HOME=<mount-path>` to redirect writes that would otherwise go to
`/root/` (inaccessible to non-root users):

```bash
-v /etc/passwd:/etc/passwd:ro \
-v /etc/group:/etc/group:ro \
-e "HOME=/cache" \
--user "$(id -u):$(id -g)" \
-v "$CACHE_DIR:/cache"
```

### Pattern 2: ACL fallback (when the image requires root)

Some images hardcode root in their entrypoint and cannot use `--user`. For these,
keep the container running as root but set ACLs on host directories so root-created
files remain accessible to the host user:

```bash
setfacl -R -m "u:$HOST_USER:rwx" /data/cache/<service>
setfacl -R -m "d:u:$HOST_USER:rwx" /data/cache/<service>
```

The `d:` (default) ACL ensures **future** files/dirs inherit the permission, so the
container can be recreated repeatedly without losing access.

### One-click fix script

Run `sudo bash scripts/fix-data-permissions.sh` to apply both ownership and ACLs.
Safe to run at any time — it only touches directories containers write to, leaving
container runtime storage (`/data/docker/`, `/data/containerd/`) untouched.

## Known Pitfalls & Fixes
Troubleshooting is documented per-node in `nodes/<hostname>/README.md`.
A fix that generalizes across machines becomes a convention here or a shared script
under `scripts/` — anything machine-specific stays in that node's README.

## Machine Discovery

Before any operation on a managed node, run:
```bash
source scripts/lib/discover.sh
```
This auto-detects the current machine and exports environment variables pointing to
its config directory under `nodes/`. If the machine is not yet registered, it prompts
to create one by copying an existing similar node.

**Important**: If the user does not explicitly specify a target machine, always run
`source scripts/lib/discover.sh` first to auto-discover the current environment and
operate on the detected node.

## Agent vs User Responsibilities

This project manages bare-metal machines. Many operations require physical access,
root privileges, or irreversible system changes. The boundary is:

### Agent Responsibilities (read-only, project-scoped)
- Run `source scripts/lib/discover.sh` to detect the current machine
- Run `bash scripts/lib/hardware-info.sh` to collect hardware information
- Read and edit files within the project directory (nodes/, CLAUDE.md, inventory/, benchmark/)
- Run benchmark scripts
- Analyze hardware reports and document findings

### User Responsibilities (physical access or root required)
- All provisioning steps documented in `nodes/<hostname>/README.md`
- OS installation and partitioning
- Network configuration (Ethernet, WiFi)
- Package installation (`apt install`, driver installation)
- System-level configuration (`/etc/` files, GRUB, kernel modules, Docker daemon)
- Any `sudo` command that modifies system state

Agent permissions are enforced in `.claude/settings.json`.

> **Project spirit**: Every fix becomes a config or a doc page, so the next machine is forged faster and more reliably.
